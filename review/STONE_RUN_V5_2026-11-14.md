## 4. 失败原因

### 4.1 v5 修复本身是有效的（木制阶段大幅提前）

- 首个 log：**669**（v4 4615、v3 1983、v2 1651）；木镐：**1981**（v4 5034，占 33% 而非 84%）。
- `agent.log`：`log broken` **8 次**（v4 70 次，其中 65 次为假破坏）；`pickup: reached drop point` 3 次、`pickup: blocked -> jump/sidestep` 11 次；`dig_stall` **0 次**（v4 的 851 步 walk 空转未复现）。
- 说明 v5 的「阈值 55 + 朝掉落点定向 + 停滞恢复」把木制阶段从 84% 预算压到 33%，方向正确。

### 4.2 真正的失败点：熔炉阶段「工作台不可达且无备用台」

在 8 圆石到手（步 2936）后，石器分支进入 `cobble >= 8` 且 `want="furnace"` 的路径：

1. `_near_table()` 要求 `|Δy| <= 2.0` 且 3D 距离 `<= 3.0`；台子在 y=69，agent 已下挖到 y=46（Δy≈23），判定为「不在台旁」——这是正确的。
2. `_table_step()`：`tables=0`（台子已被放下、不在背包），无法放置；`planks=3 < 4` 且 `log=0`，也无法合成新台子；返回 `None`。
3. 于是 `dep_fail += 1`，最多 80 帧 `seek_and_break(LOG_BLOCKS, up_scan=True)`；80 帧后打印 `stone dependencies unavailable -> explore for wood` 并走 `walk_policy`，循环往复 37 次。
4. 深层地下没有木头，nav 反复 `stuck -> jumping` / `jump failed -> digging` / `dig timeout(40) -> detouring`，把剩余 3064 步耗尽；18 圆石始终没有变成熔炉。

**最小根因**：唯一的工作台在 2492 被放在矿口（y=69），随后 agent 下挖 23 格到 y=46；代码没有「走回已放置台子」的路径，也没有预留第二张 portable 台（或预留 4 木板）——熔炉所需 8 圆石早已足够，缺的只是台子服务性。

### 4.3 不是旧问题复现

- 放置失败：仅 2492 那次出现 7 次失败尝试后**确认成功**（v5 放置恢复生效），不是 v4 的竖井放置死锁。
- 拾取：不再有 v4 的 70 次假破坏 / 16 步盲走。
- deadline：无重启囤木；`dig_stall` 0 次。
- 运行层：`ExitCode=0`、无 OOM、无网络、无模型调用（tokens/calls 0）。
